# Software Test Plan

## Objective

Verify that FizzSort meets every baseline requirement in
`docs/requirements.md` on its supported compiler and operating-system matrix.

## Test levels and types

- **Unit:** nominal sorting, boundary inputs, custom ordering, stability,
  descending-run handling, deterministic reporting, and injected comparator
  failure.
- **Integration/property:** deterministic generated inputs are compared with
  Rust's standard stable sort over lengths 0 through 299 and duplicate-heavy
  data spanning multiple runs.
- **Documentation:** public examples compile and execute as doctests.
- **Compatibility:** tests execute on current stable Rust for Linux, Windows,
  and macOS, plus Rust 1.74 on Linux.
- **Static analysis:** compiler warnings and Clippy findings are treated as
  errors; formatting and rustdoc warnings are gates.

## Environment

GitHub-hosted runners use the toolchains declared in
`.github/workflows/assurance.yml`. Local tests may run on any supported Rust
host. The CI log records runner image, commit, toolchain setup, commands, and
outcomes.

## Entry criteria

- Requirements and design are available in the repository.
- The source compiles on the selected toolchain.
- Test code is configuration-controlled with the implementation.

## Pass/fail criteria

A revision passes only when every CI job and every invoked test exits with code
zero. Warnings in lint or documentation jobs are failures. A failed test blocks
release until the defect is corrected or the baseline is explicitly revised.

## Regression and repeatability

The complete automated suite runs for every push and pull request. Test data is
fixed or generated by a fixed, locally implemented sequence, with no network,
clock, randomness, or shared-state dependency during test execution.

## Results and anomaly handling

GitHub Actions logs are the test record for each commit. Failures remain visible
on the commit and pull request. Defects are tracked with GitHub issues when they
cannot be corrected in the originating change.

## Coverage limitations

The current baseline uses behavior-driven cases and broad deterministic stress
tests but does not claim structural coverage percentages or MC/DC. Such
evidence is outside the needs of this non-safety-critical library and would be
required separately by any safety-critical adopter.
